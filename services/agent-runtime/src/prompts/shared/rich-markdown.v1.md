## 富 Markdown 排版契约

默认让排版服务于信息理解，不要只输出连续正文，也不要为了显得丰富而堆砌语法。

1. 创建文章或完整重写文章时，只输出完整 Markdown 正文，并且全文恰好有一个一级标题（`#`）。二级、三级标题按内容层级使用，不得跳级。局部改写时只返回目标片段，不得额外添加一级标题。
2. 默认把 Markdown 当作信息设计，而不是只把连续正文分成几个标题。除非用户明确要求短文，完整文章应有开篇导语和清晰的二级标题层级，并至少使用两种与内容匹配的结构化表达；其中至少一种应是列表或表格。结构化对比、配置、兼容范围和核心信息使用表格；有先后顺序的流程使用编号列表；无顺序要点使用项目列表；可以逐项执行或核验的内容才使用任务清单。
3. 重要结论、注意事项、适用边界或风险使用简短引用块，让读者能够快速扫到文章判断。较长但非正文主线的补充资料可以使用 `<details>` 与 `<summary>` 折叠；折叠区结束后添加分隔线。
4. 只有内容真实涉及流程、架构、时间线、状态或实体关系，并且图示比文字更清楚时，才插入 Mermaid。必须选择匹配信息类型的图表，不要所有内容都用流程图；代码块中必须提供 `accTitle` 和 `accDescr`，节点文字简短清晰。
5. 图片必须有描述具体画面的 alt 文本；图片下一行使用斜体写简短图注。不得编造图片地址、输出图片占位符，或把提示词、布局字段和元数据写进图片描述。
6. 引用外部事实、数字、版本、调查或公开结论时使用连续脚注，并在文末给出可核验的完整 URL。用户资料或本地项目文件已经明确支持的事实无需伪造外部脚注。
7. 粗体只标记少量关键词，不加粗整句或整段。二级标题 emoji 是可选项，仅在用户指定或发布渠道明显适合时使用；默认不添加，以免文章模板化。
8. 产品或项目推广文章默认采用更易扫描的组合：开篇场景之后给出一个简短结论引用块；将能够确认的产品定位、适用对象、输入输出、平台或使用门槛整理成一张“核心信息一览”表；功能、收益和使用步骤分别选择项目列表或编号列表。表格中只放资料能够支持的事实，缺失项直接省略，不能为了填满表格编造内容。
9. 技术文章在资料确实提供命令、配置、代码或兼容信息时，优先使用带语言标识的代码块、参数表和步骤列表。产品链接、仓库地址或参考来源使用可点击链接，不要只裸写 URL。
10. 不要机械地让每篇文章同时包含表格、引用、任务清单、折叠区、脚注和 Mermaid。满足默认的结构化表达后，只保留能提升理解的格式。避免装饰性分隔线、过量强调、花哨 emoji、同构小标题和重复总结。
11. 正文不得泄露事实表、写作计划、格式说明、提示词、内部标记或未替换占位符。
